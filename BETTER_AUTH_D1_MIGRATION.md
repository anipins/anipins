# Better Auth + Cloudflare D1 migration

## Decision and current architecture

The target is Better Auth for identity/session handling, Cloudflare D1 for all structured AniPins records (accounts, profiles, artwork metadata, likes, subscriptions, and related records), Cloudflare R2 for image/file objects, and Workers for APIs/security/integrations. The artwork bytes and R2 object keys must remain unchanged.

The live site remains a Next.js Node.js application in a Cloudflare Container using the existing PostgreSQL/custom-session path. A separate `anipins-migration-staging` Worker now exercises the Better Auth + D1 app bridge on isolated D1/R2 resources. The production D1 target is populated but is not yet serving website or app traffic.

## Staged migration sequence

1. (Complete for staging.) Create a non-production D1 database, bind it only in staging Worker configs, and apply versioned business, Better Auth, auxiliary, and identity-link schemas. D1 migrations `0001`–`0004` are applied; `0003` provisions mobile auth tickets and the source's currently empty `anipins_build_chunks` table, while `0004` adds an explicit Better Auth-to-AniPins user link. Remote schema verification confirmed the operational tables, and Wrangler reports no pending migrations. No production database is bound.
2. (Isolated app-origin staging deployed and partially smoke-tested.) The app Worker `anipins-migration-staging` is deployed at `https://anipins-migration-staging.anipins01.workers.dev` (version `494021e9-a32f-449f-86f6-bb126fc2cb1b`) with only staging D1/R2 bindings. It serves Better Auth at `/__staging/auth/*`. Staging email sign-up/session, D1 identity handoff to the container, browse/detail, public thumbnail fetch, authenticated like/unlike, sign-out, anonymous Premium denial, and anonymous admin denial passed. The secure-prefixed Better Auth cookie is now correctly resolved by both the Worker bridge and Better Auth session lookup. Google OAuth and an authenticated administrator upload are not yet tested. Staging is not production, and production app traffic remains on the legacy path.
3. (Partial staging data import.) Imported 1,877 public artwork metadata rows into staging D1 in idempotent batches and 4 non-payment public settings. Source and destination matched on exact row count, sum/min/max IDs, combined original/thumbnail reference lengths, views, and downloads. Artwork bytes and R2 objects were not copied or changed. No user PII, password hashes, sessions, device tokens, admin audit/security records, or billing records have been copied to staging. Live Razorpay settings were deliberately excluded. This is a staging validation copy, not the final production migration.
4. Route the app's structured-data adapter to D1 and remove Postgres-specific SQL assumptions. Keep authorization (admin role and Premium status) sourced from trusted D1 records.
5. Build and validate an idempotent export/import for every structured table. Preserve IDs or create and verify explicit mappings for users, artwork, likes, collections, subscription/billing history, security records, and all foreign keys. Keep R2 objects and keys untouched.
6. Validate email/password, Google sign-in, logout, session expiry/revocation, account switching, mobile ticket exchange, admin 2FA, account deletion, artwork CRUD, likes/saves, Premium checks, and billing webhooks in local/staging D1 using test-only accounts.
7. Remove runtime Supabase/Postgres dependencies only after parity checks pass. Keep the current production services available for rollback until the production cutover is separately approved and verified.
8. Migrate production data only after source export access is reliable, counts/checksums reconcile, and recovery/rollback are verified. Revoke old sessions at cutover so stale custom sessions cannot remain valid.

## Boundaries and blockers

- The production D1 snapshot has not had a verified export/restore or production end-to-end test. App-origin email sign-in and the D1 identity handoff are verified on isolated staging only. Production `BETTER_AUTH_SECRET` and `D1_RPC_SECRET` are present on the production-routed Worker, but `GOOGLE_CLIENT_SECRET` is absent from both migration staging and production. Google OAuth therefore remains unverified. Existing app-managed admin 2FA is still supported through the login page's explicit existing-sign-in fallback; it has not been ported to Better Auth. The legacy multi-account session switcher remains unavailable in Better Auth mode.
- The app Worker's current `wrangler.jsonc` is named `anipins-staging` but binds the existing `anipins-public-media` and `anipins-premium-media` R2 buckets. A dry-run confirmed those bindings. It was not deployed, because deploying that config would publish code against the production artwork buckets and may restart the app Container; an isolated staging Worker/Container with non-production storage and secrets is required first.
- The app still uses PostgreSQL and has Supabase storage/auth-related configuration and fallbacks. Supabase has not been fully removed.
- Current Supabase inventory includes 20 public tables. `public.anipins_build_chunks` has zero rows and was missing from the checked-in bootstrap schema; its D1 destination was added in migration `0003`. There is also a source security finding: `public.billing_subscriptions` has RLS disabled (6 rows). Do not enable RLS blindly, because that may block legitimate service access; define and review policies before changing it.
- The Supabase storage restriction is separate from this cutover. Existing R2 objects/keys remain untouched; the staging buckets contain only two validation image samples. Do not remove remaining Supabase data until source parity and rollback have been verified.
- Production data migration requires reliable source export. The D1 target currently has a point-in-time copy but no verified export/restore. Do not delete existing users/sessions, billing records, artwork metadata, or disable the old auth path until final parity and end-to-end tests pass.

## Rollback

Security guard added during local continuation: the staging identity bridge rejects any AniPins ADMIN with legacy TOTP enabled until the second-factor challenge is migrated. It does not disable the legacy production challenge and does not constitute completed 2FA migration.

Before production cutover, restore the prior Worker version and keep the existing PostgreSQL auth tables intact. If any accounts are created through Better Auth during a staged period, do not assume they exist in PostgreSQL; reconciliation must be completed before switching back. Production rollback and account-data reconciliation require a separate runbook before any live cutover.
